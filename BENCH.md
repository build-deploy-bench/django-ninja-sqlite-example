# Build-deploy benchmark fixture: Django Ninja + SQLite

Copy of [c4ffein/realworld-django-ninja](https://github.com/c4ffein/realworld-django-ninja) at
`87dd078c883a046f5ff20269df2fb004d8b5f83f` (2026-11-02), MIT license (kept in `LICENSE`). The first commit is
the unmodified upstream tree, including its three submodule gitlinks; the second commit holds all the patches.

## Patches

- Removed the submodules (frontends, RealWorld spec), the root `Dockerfile`, `docker-compose.yml`, and the
  upstream CI workflows. A root `Dockerfile` changes build detection on Railway, Fly and Vercel.
- `gunicorn==26.2.0` added. `psycopg2==2.9.6` replaced by `psycopg2-binary==2.9.13`: `helpers/exceptions.py`
  still imports it, and the source package needs libpq headers and a compiler that differ per provider.
- `requirements.txt` is the lockfile (hashed, generated by uv; the regenerate command is in its header).
  Install uses `pip install --require-hashes`.
- `.python-version` = `3.12.16` (upstream ignored the file; now committed). Docker images use
  `python:3.12.16-slim-bookworm`.
- Settings: `DATABASE_URL=sqlite:////abs/path` selects file SQLite with `DEBUG` off (upstream allowed SQLite
  only with `DEBUG=True`). `SECRET_KEY` comes from the environment and is required when `DEBUG` is off.
  Production runs with `DEBUG` off.
- `GET /version` returns `{"commit": "<sha>", "run": "<id>", "deployment": "<id>"}`. `bench/build.sh` writes `.build-commit` from `BENCH_COMMIT`,
  `RENDER_GIT_COMMIT`, `RAILWAY_GIT_COMMIT_SHA`, `VERCEL_GIT_COMMIT_SHA`, then `git rev-parse HEAD`, else
  `unknown`. `run` is the runtime env var `BENCH_RUN_ID` (else `unknown`). The harness sets it before each deploy, so it identifies the deployment even when the commit is the same. `deployment` is `RAILWAY_DEPLOYMENT_ID` (else `unknown`): Railway gets no `BENCH_RUN_ID`, because a changed variable invalidates part of its build cache. The endpoint does not touch the database.
- `bench/build.sh {install|build|all}` with the `::bench::install_start/done` and `::bench::build_start/done`
  markers. Install = `pip install` of the lockfile (it creates `$VIRTUAL_ENV` first if it is missing, which
  Railpack needs). Python has no build the app needs; build = `python -m compileall` of the app sources plus
  writing `.build-commit`, so the build phase is short (well under 1 s).
- Every `::bench::` marker ends with the wall-clock time in epoch milliseconds. At runtime, `::bench::start` marks the start of the start command and `::bench::listening` marks the bound listen socket. `bench/start.sh` prints the start marker; `bench/gunicorn.conf.py` prints the listen marker.
- `bench/start.sh`: puts a repo-local `.venv` on `PATH` if one exists, defaults
  `DATABASE_URL=sqlite:////tmp/conduit.sqlite3` and `ALLOWED_HOSTS=*`, runs `manage.py migrate`, then
  `exec gunicorn config.wsgi --bind 0.0.0.0:$PORT` (1 sync worker). The database is empty on every new
  instance.
- `Dockerfile.fly` and `Dockerfile.vercel` (identical below the header), `fly.toml`, `vercel.json`.

## Commands

| | |
|---|---|
| Install | `./bench/build.sh install` |
| Build | `./bench/build.sh build` |
| Start | `./bench/start.sh` |
| Health path | `/api/tags` (200, `{"tags": []}`) |
| Commit check | `/version` |
| Env vars | `SECRET_KEY` (random, per provider). Nothing else is required. |

## Providers

### Render

- https://bdb-django-ninja-sqlite.onrender.com
- Native Python runtime, region `virginia`, plan `starter` (paid, always on) with build plan `starter` (same as the Node service),
  1 instance. Build command `./bench/build.sh all`, start command `./bench/start.sh`, health check
  `/api/tags`, auto-deploy off. Env: `SECRET_KEY`.
- Render reads `.python-version` (`Using Python version 3.12.16 via .../.python-version`) and installs into
  `/opt/render/project/src/.venv`.
- The API cannot change a free service to a paid plan, so the service was recreated on the Starter plan.

### Railway

- Project and service `bdb-django-ninja-sqlite`, environment `production`,
  https://bdb-django-ninja-sqlite-production-6c47b1a2.up.railway.app
- Railpack 0.43.0, Python 3.12.16 from `.python-version`. `RAILPACK_INSTALL_CMD=./bench/build.sh install`,
  build command `./bench/build.sh build`, start command `./bench/start.sh`, health check `/api/tags`,
  1 replica in `iad` (`us-east4-eqdc4a`). Env: `SECRET_KEY`. Plan: `pro`. Auto-deploy disabled with
  `serviceInstanceAutoDeployUpdate`; `serviceInstanceAutoDeployStatus` returns `enabled: false`.
- `RAILWAY_GIT_COMMIT_SHA` reaches the build.
- Railpack difference: with a custom install command, Railpack still sets `VIRTUAL_ENV=/app/.venv` and copies
  that path into the image, but it does not create the venv or put it on the runtime `PATH`. `bench/build.sh`
  and `bench/start.sh` handle both.

### Vercel

- Team `build-deploy-bench`, project `bdb-django-ninja-sqlite`, https://bdb-django-ninja-sqlite.vercel.app
- Container Runtime: `vercel.json` sets `framework: container` and `git.deploymentEnabled: false`;
  `Dockerfile.vercel` is built with Buildah. Env: `SECRET_KEY` (production, sensitive). No `PORT` set; the image
  listens on 80. `/tmp` is writable, so the same SQLite path works.
- Open item: a `vercel deploy` from a `git archive` returned `unknown` from `/version`.
  `vercel deploy --build-env BENCH_COMMIT=<sha>` did not reach the Dockerfile `ARG`, and a CLI upload has no
  `VERCEL_GIT_COMMIT_SHA`. Test the harness path (API deployment with `gitSource`) for `VERCEL_GIT_COMMIT_SHA`,
  or a project-level env var. The probe now identifies a deployment by `run` (`BENCH_RUN_ID`, set per deployment
  with `vercel deploy --env BENCH_RUN_ID=<id>`), so the commit is no longer needed for that.

### Fly.io

- App `bdb-django-ninja-sqlite`, https://bdb-django-ninja-sqlite.fly.dev, region `iad`,
  1 Machine, `shared-cpu-1x` with 1 GB (the `fly launch` default), always on. Secret: `SECRET_KEY`.
- Deploy: `flyctl deploy --config fly.toml --app <app> --ha=false --build-arg BENCH_COMMIT=<full sha>` from a
  clean `git archive` of the commit. The harness must pass `BENCH_COMMIT`, or `/version` returns `unknown`.
- Open item: three deploys with the Depot builder failed with `connecting to Depot builder: timed out
  connecting to machine` before any build step; Fly's own remote builder (`--depot=false`) worked. Check Depot
  again before benchmark runs, since the Node pilot uses Depot.
